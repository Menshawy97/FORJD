# FORJD — Architecture Rules

Read this file and the relevant `docs/architecture/*.md` before modifying code.
Implement only the requested vertical slice — migration → domain model → repository →
API endpoint → tests → Flutter screen, for one bounded capability. Do not implement
adjacent features "while you're in there."

The execution plan lives at `docs/product/roadmap.md`. The reasoning behind major
decisions lives in `docs/decisions/` as ADRs — read the relevant one before disagreeing
with a rule below, and add a new ADR before overturning one.

## The four things that must be exceptionally well designed

Everything else can evolve around these. See `docs/architecture/system.md`.

1. **Canonical health model** — `HealthObservation`, not provider-specific shapes.
2. **Provider/integration abstraction** — `HealthProvider`, `AuthProvider`, `StorageProvider`.
3. **Workout engine** — template/session split, extensible block types.
4. **Longitudinal analytics model** — raw → normalized → aggregated → derived → insight.

## Rules

1. Domain code must not depend on UI.
2. Domain code must not depend on provider SDKs.
3. Health providers implement `HealthProvider`. The workout engine never calls
   WHOOP, HealthKit, or Health Connect directly.
4. External integrations must be isolated in `integrations/` (mobile) or
   `integrations/<provider>/` (API).
5. No secrets in mobile source. WHOOP/OAuth secrets live server-side only.
6. Workout execution must work offline. The network is never in the critical path
   of a live workout session.
7. API changes require versioning (`/api/v1/`, then `/api/v2/`), never breaking
   changes to a shipped version.
8. New features require tests: contract tests for adapters, golden fixtures for
   the InBody parser, unit tests for training/analytics calculations.
9. Never directly mutate analytics aggregates. They are derived from raw/normalized
   data by the aggregation jobs — recompute, don't patch.
10. Health data must preserve source. Never overwrite one provider's observation
    with another's; store both and apply the source-priority policy at read time.
11. Supabase is reached only through `AuthProvider` / `StorageProvider`. No Supabase
    SDK calls in business logic, ever.
12. RLS is defense-in-depth. Authorization rules live in NestJS guards, never only
    in SQL policies — a rule that exists only in SQL is a rule you can't unit test.
13. No business logic in Supabase Edge Functions. NestJS is the only application layer.
14. Schema changes are versioned migrations committed to the repo, generated by
    drizzle-kit. Never hand-edited via the Supabase Studio UI.
15. Health data never reaches an analytics or advertising SDK — not once, not
    "just for debugging." This is Apple Guideline 5.1.3(i) and Google's equivalent,
    made into an engineering rule, not just a policy statement.
16. HealthKit/Health Connect code does not merge until it has run on a physical
    device (Android phone for Health Connect, iPhone via TestFlight for HealthKit).
    A green CI build is not done. See `docs/decisions/ADR-007-no-mac-ios-toolchain.md`.
17. The `health` package (pub.dev) is an implementation detail behind `HealthProvider`.
    No feature code imports it directly, and every `HealthObservation` records its
    originating provider explicitly — never inferred from which API returned it.

## Enforced, not just stated

From Phase 1, CI includes a grep-based conformance check that fails the build if:
- the Supabase SDK is imported outside the provider adapter directories,
- the `health` package is imported outside `integrations/`,
- domain packages (`packages/domain/**`) import anything from UI or provider SDKs.

If you're about to violate one of these rules "just this once," don't — fix the
CI check or update the ADR that justifies the exception first.

## Product context (one paragraph)

FORJD unifies training (weightlifting, running, HYROX, etc.), wearable/health data
(Apple Health, Health Connect, WHOOP), and InBody body-composition scanning into one
canonical model, with AI features layered on top — instead of three separate apps.
The core bet is the canonical model and provider-adapter pattern: every external
source normalizes into `HealthObservation` / `Exercise` / `WorkoutSession`, so adding
a new provider or modality is an adapter, not a rewrite.

## Platform note

Development happens on Windows. Android is the primary dev/test platform. iOS ships
without owning or renting a Mac — see ADR-007 for the full strategy (the `health`
package, Codemagic automatic signing, TestFlight validation on a physical iPhone).
Do not write Xcode-project-level native Swift unless the `health` package genuinely
cannot express what's needed; when that happens, keep the native code behind the
unchanged `HealthProvider` interface (rule 3).

## Docs are memory

If a session changes the design of something documented in `docs/architecture/*.md`,
update that doc before ending the session. If a session makes a decision worth
remembering later (a library choice, a reversal, a tradeoff), write an ADR. These
docs are what keeps week 40 as coherent as week 3 — they are not optional ceremony.
