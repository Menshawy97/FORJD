# Phase 12D — notification switches move to the server

**Status (2026-10-05): built (slices 1-5), in review.** One slice, one PR, test-first, reviewed, merged with `main` green. No new screen: the Notifications
screen looks and behaves as it does today.

**Scope the owner chose (2026-10-05):** the five switches only. The quiet-hours editor is **out**: the
design has only a stub for it (`docs/design/slice2-screen-specs.md` §5.5), so it needs a mock-up the owner
approves first, and it can be added later without a breaking change.

## Why now, and what it does not do

Today the five switches (workout reminders, recovery alerts, PR celebrations, leaderboard moves, weekly
summary) live only on the phone (`store/notification-preferences.ts`, AsyncStorage). The server cannot
know them, so a push sent from the server (12F) could not respect them, and a new phone starts with
defaults. This slice makes the server the home of the choice and keeps the phone's copy as a cache.

It changes nothing a person can see. **Nothing reads these switches yet**: local reminders (12E) and push
(12F) come later. Building the storage first is cheap and additive, and it is why the roadmap lists it as
12D.

## What exists

- `store/notification-preferences.ts`: five booleans, the defaults (`rank` off, the rest on), a load that
  falls back to the defaults, and a save that never throws. Its docblock already says moving them
  server-side is "an adapter swap here, not a screen rewrite".
- `app/notifs.tsx`: toggles apply and persist immediately, no Save button, no toast.
- `preferences.notifications_enabled` (server): a single unwired boolean, never read or written.
- `PATCH /users/me/privacy` and `PUT /users/me/timezone`: the two existing per-user settings routes.
- Sign-out already clears the device copy (`NOTIFICATION_PREFERENCES_STORAGE_KEY`, review L5-2).

## Design

**Table.** A new `notification_preferences` table, one row per user: `user_id` (primary key, cascade
delete), five booleans (`workout`, `recovery`, `pr`, `rank`, `weekly`), `updated_at`. Generated by
drizzle-kit (rule 14). No row means "never saved". Quiet-hours columns are **not** added now; they arrive
as a later additive migration with their editor. The unwired `preferences.notifications_enabled` is left
alone and its comment updated to point here, so nobody mistakes it for a master switch.

**API (additive, `/api/v1`, rule 7), both behind `JwtAuthGuard`:**

- `GET /users/me/notifications` returns the five booleans and `updatedAt` (`null` when never saved, in
  which case the booleans are the defaults).
- `PATCH /users/me/notifications` takes any subset of the five booleans (at least one), upserts the row,
  and returns the same shape. A partial update means two phones changing different switches do not undo
  each other.
- Authorization is by the caller's own id only; there is no way to name another user (rule 12). The
  defaults live in `@forjd/domain` so the API and the phone share one copy.
- Contracts in `packages/contracts` with a pinned fixture; the account export gains the five booleans
  (additive, `version` stays 1); `data-inventory.md` gains a row (collected at the Notifications screen,
  stored in `notification_preferences`, in export, removed by deletion by cascade).

**Phone.** `store/notification-preferences.ts` keeps its public functions, so the screen does not change:

- `load`: returns the device copy at once (the screen never waits on the network), then refreshes it from
  the server in the background and updates the screen if the server's answer differs.
- `save`: writes the device copy first, then sends the changed switch to the server. A failed send is not
  an error the person sees; the change is remembered as unsent and retried on the next open of the screen
  and on the next app launch. The switches are never in the critical path of a workout (rule 6).
- **The server always wins** (owner decision). Whatever the server answers replaces the device copy. There is
  no upload of existing device choices: every account starts from the defaults until it saves a change
  (owner decision; nobody had set switches that mattered, and nothing reads them yet).
- Sign-out clears the device copy as it does today; the next account starts from its own server row.

## Slices (inside the one PR, in order, each test-first)

1. **Domain and contracts:** `NOTIFICATION_PREFERENCE_KEYS`, defaults, the request and response schemas,
   fixture, export field. Specs first.
2. **Migration and repository:** the table, `get` and `upsert`, a repository spec against real Postgres
   (no row reads as defaults, partial update keeps the other four, a second user's row is untouched).
3. **Service and controller:** the two routes, validation (empty body refused, unknown key refused), an
   e2e test over real HTTP proving one user cannot read or change another's, and the account export and
   deletion specs extended.
4. **Phone store:** the cache, background refresh, unsent-change retry, and sign-out;
   tests for each, plus the existing screen tests left green and unchanged.
5. **Docs:** `data-inventory.md`, `roadmap.md`, the `preferences` schema comment, this plan's status.

## Not in this slice

The quiet-hours editor and its columns; reading the switches anywhere (12E, 12F); a master "all
notifications" switch; push tokens (12F); any change to what the screen shows.

## Risks

- **A stale phone overwriting a newer choice.** Sending only the switch that changed (not all five)
  keeps this to the single switch.
- **Choices set on a phone before this change are dropped.** Accepted by the owner: every account starts from the defaults, and nothing reads the switches yet.
- **A failed migration locally.** The local database needs `pnpm --filter @forjd/api db:migrate` and
  Docker running before the repository specs will pass (they did not before 2026-10-05 for exactly that
  reason).

## Owner decisions (2026-10-05)

1. **At the changeover, start everyone fresh from the defaults.** Choices already saved on a phone are not uploaded.
2. **If a phone and the server disagree, the server wins**, so every device shows the same answer.

## As built (2026-10-05)

Matches the plan, with these differences:

- **An unsent change is retried when the Notifications screen opens, not also at app launch.** Nothing reads
  the switches yet (12E and 12F come later), so a launch-time retry would add a place that runs on every start
  for no benefit. Add it when push needs the server copy to be current.
- **The sync lives in its own module**, `apps/mobile/src/store/notification-preferences-sync.ts`, beside the
  existing device store, which is unchanged apart from taking its defaults from `@forjd/domain`. The
  unsent-change key is defined in the device store and re-exported, because sign-out must forget it and the
  sync module imports the API client (a cycle through secure storage).
- **A tap during the open-time fetch wins for that visit.** If the person taps a switch before the server's
  answer arrives, the screen ignores that answer; their change is sent and the next open adopts the server.
- **Migration `0032_notification-preferences`**, generated by drizzle-kit. The account export gained
  `notificationPreferences` (`null` when never saved); the deletion e2e lists the new table.
- Owed on a phone: nothing new. This slice has no native code, so there is no device walk to add.
