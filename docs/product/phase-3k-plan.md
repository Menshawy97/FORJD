# Phase 3K — programs

The final Phase 3 slice. A program is a named, multi-week plan the athlete *follows*: it groups
several workouts, one of them is recommended next, and Home and Train both change while one is
active.

Two decisions were put to the user before planning and answered by them:

1. **Seed the nine programs the design actually specifies**, as a versioned migration — not the
   "24 structured programs" the Train hero card advertises. The prototype's `workoutsForProgram`
   table names every workout of all nine and every exercise of each, so seeding them invents
   nothing. Inventing fifteen more would mean writing training progressions and labelling them
   `5/3/1` or `Race Prep 10K`, which is fabricated training advice — the one thing this project
   has consistently refused. **The hero card's copy must be corrected to the real count** rather
   than left as a number the app cannot back.
2. **Phase K covers the whole surface, including the builder** — the catalogue, the program
   overview, follow/unfollow, Home's active-program branch, Train's sections, and
   `s_programBuilder()`.

## A correction to the phase outline

`phase-3-plan.md` sketches Phase K as `programs → program_weeks → program_days`. **The design
does not work that way**, and building to that outline would produce a calendar the screens
never ask for.

Read `s_programOverview()` and `workoutsForProgram()`: a preset program is **a set of named
workouts** plus a duration string (`4 days · 8 weeks`) and a level. There are no per-week rows
and no per-day rows. Day-of-week assignment (`assign`, `Mon`–`Sun`) exists only in the
*builder*, for custom programs — and even there it maps a day to one of the athlete's own
workouts, not to a distinct entity.

So the tables below are `programs → program_workouts`, with the weekday living on the join row
where the design actually puts it.

## The load-bearing insight: a program's workouts *are* workout templates

The overview's workout rows open `workoutDetail`, and their `Start` button calls
`startRoutine(wn)` — the same call Train's "My Workouts" rows use. A program's workout behaves
identically to a template because it *is* one.

This costs nothing to adopt and saves a whole parallel structure:

- `workout_templates` already allows `ownerUserId = null` for catalogue rows, and
  `visibleTo(userId)` already reads `owner is null or owner = :user`. Preset program workouts are
  catalogue templates, visible to everyone, by machinery that already exists and is tested.
- Starting a program workout reuses `workout/[id].tsx` and its existing `PendingLiveSession`
  handoff. No second path into the live screen.
- A custom program assigns the athlete's *own* templates to weekdays, which is exactly what the
  builder's `assign` does.

## Schema

Three new tables. One migration, generated by `drizzle-kit` and committed (rule 14).

```
programs
  id, owner_user_id (null = catalogue preset), name, slug,
  category (strength | hybrid | running | cross_training),
  level (beginner | intermediate | advanced),
  days_per_week int, duration_weeks int, description text,
  version int not null default 1,
  deleted_at, created_at, updated_at
  index (owner_user_id), unique (slug) where owner_user_id is null

program_workouts            -- the join described above
  id, program_id, template_id (-> workout_templates, restrict),
  order_index int,
  day_of_week int null      -- 0-6 like Date#getDay(); null for a preset,
                            -- which prescribes a set of workouts, not a calendar
  index (program_id, order_index)

program_enrollments
  id, user_id, program_id,
  program_version int       -- snapshotted at enrolment, see below
  started_at, ended_at null -- null = active
  index (user_id)
  unique (user_id) where ended_at is null   -- one active program at a time
```

**One active program at a time** is enforced in Postgres by that partial unique index *and* in a
NestJS service check, per rule 12 — a rule that exists only in SQL is a rule that cannot be
unit-tested. The design assumes singularity throughout: `activeProgram` is a single string, and
Train renders one "Currently following:" chip.

### What `program_version` actually buys, and what it does not

The phase outline's intent is that "updating a program's content never rewrites someone's
in-flight 12-week cycle". Storing a version number on the enrolment only delivers that if
content is **immutable per version** — otherwise the column records which version they *joined*
while they silently read the mutated current one.

So the rule is: **editing a program bumps `version` and rewrites `program_workouts`; enrolments
carry the version they started under.** Phase K ships the column, the bump, and a test proving
an edit does not change what an existing enrolment records. Serving an enrollee the *older
content* is deliberately **out of scope** — it needs per-version content rows, a bigger change
than this phase should carry, and nothing in Phase K edits a preset program to trigger it.
Record it as a known gap rather than pretend the column already does more than it does.

## Slices

Each is its own PR: docs first, tests green, merge, confirm CI on `main`.

### K1 — schema and the seed

The migration, the three tables, and the seed of nine programs plus their catalogue templates.
Content comes verbatim from the prototype's `workoutsForProgram` table and `s_catalog`'s own
`progs` array (name, category, `4 days · 8 weeks`, description, level).

#### The exercise names do not resolve, and this was measured

**Do not assume the prototype's exercise names match the catalogue.** They were checked against
the real 876-row catalogue before this plan was written, and only **4 of 28 match exactly**.

**Fuzzy matching is not an option** — it is confidently wrong, which is worse than failing. A
shortest-substring match resolves:

| Prototype name | What fuzzy matching picks | Why that is wrong |
|---|---|---|
| `Bench Press` | Machine Bench Press | A machine press in a 5/3/1 Bench Day |
| `Walking Lunge` | Lunge Sprint | A different exercise entirely |
| `Dips` | Ring Dips | A much harder variation |
| `Lat Pulldown` | V-Bar Pulldown | An arbitrary grip |

So the seed carries an **explicit, hand-curated `name → slug` map**, reviewed once, with no
fuzzy fallback. It **fails loudly on any unresolved entry** rather than skipping it: a program
missing a lift is worse than a seed that refuses to run.

#### Four names have no catalogue equivalent at all

`5K Run` and `Tempo Intervals` return nothing — free-exercise-db is a *resistance-training*
database, and three of the nine programs (Race Prep 10K, Couch to 5K, and half of Hybrid
Athlete) are built almost entirely on them.

**Decision, taken with the user: add them as curated catalogue exercises.** The `exercises`
schema already carries `measure` (`weight | time | distance`), and the app already plans a
running screen, so a distance-measured `5K Run` and a time-measured `Tempo Intervals` are real
gaps in the catalogue rather than inventions. `Assault Bike` maps to the existing `Air Bike`;
`Overhead Press` and `Pistol Squat` exist under other names and need a careful pick, not a
guess.

Keep these new rows to the smallest set the nine programs actually reference, and give them a
distinct `source` so they stay distinguishable from ingested ones.

Verify: repository tests against real Postgres, a test asserting all nine programs seed, and —
most importantly — **a test that fails if any mapped name stops resolving**, since the catalogue
is re-ingested and a rename would otherwise silently hollow out a program.

### K2 — the read API

`GET /programs` (the catalogue, filterable by category), `GET /programs/:id` (overview: metadata
plus its workouts), and `GET /programs/enrollment` (the active one, or null).

Contracts, service, controller, e2e. Watch the route-ordering trap J-c documents:
`@Get("enrollment")` must be declared **above** `@Get(":id")`.

### K3 — enrolment

`POST /programs/:id/enrol` and `DELETE /programs/enrollment`. The one-active-program rule
enforced in the service, not only by the index. Enrolling while already enrolled ends the
previous enrolment and starts the new one in a single transaction — the design's Start Following
has no "you must stop the other one first" step.

### K4 — the catalogue and overview screens

`s_catalog()` and `s_programOverview()`, against `program.png`. The category filter chips,
Follow / Stop Following, and "Recommended next" — the first workout of the program the athlete
has not completed since enrolling, derived from their sessions.

### K5 — Home and Train

Home's `goSuggested` active-program branch (`Start Workout` routes into the active program's
recommended workout rather than the generic destination), Train's "Currently following" chip,
its "My programs" list, and the "Follow a Program" hero — **whose "24 structured programs" copy
is corrected to nine here.**

### K6 — the builder

`s_programBuilder()`, against `custom program1.png` / `custom program2.png`. Name, week count,
and the `Mon`–`Sun` assignment of the athlete's own templates. The largest single screen of the
phase, which is why it is last: everything under it is proven by then.
